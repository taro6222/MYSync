# 동기화 설정과 시작 성능

## 화면 흐름

- 동기화 목록은 자동 시작/일시정지와 설정만 표시합니다.
- 동기화 추가 버튼은 별도 팝업을 엽니다. 사이드바의 추가 메뉴는 제거했습니다.
- 설정에서 현재 경로, 제외 규칙, 속도 제한을 확인하고 폴더 변경, 검사·실행, 충돌·복구, 연결 삭제를 선택합니다.
- 폴더 변경은 추가와 같은 폴더 선택 화면을 사용합니다. 저장된 계정을 연결하면 기존 원격 폴더를 다시 조회합니다. 다른 계정과 폴더도 선택할 수 있습니다.
- 설정의 작업 버튼은 아직 적용하지 않은 제외·속도 입력을 저장하지 않습니다. 해당 안내를 표시합니다.
- 검사·실행 및 충돌·복구는 실행 중인 자동 감시를 멈춘 후 엽니다.

## 폴더 변경 처리

저장 시 기존 감시가 종료될 때까지 기다립니다. 다른 프로세스가 같은 연결을 사용하면 변경을 거절합니다. 경로·계정·Provider가 바뀌면 새 연결 ID로 기존 행을 원자적으로 교체합니다. 기존 ID의 기준선과 대기열은 새 폴더에 적용되지 않습니다. 경로가 같으면 기존 ID를 유지합니다.

변경한 연결은 일시정지로 저장합니다. 설정의 검사·실행으로 변경 내용을 검토하거나 자동 시작을 누르세요. 실제 로컬/원격 파일은 이동하거나 삭제하지 않습니다. 기존 저널과 `.MYSync-recovery/<이전 ID>` 보관본은 유지합니다. 미확인 로컬 복구 기록이 있으면 폴더 변경 전에 충돌·복구에서 해결해야 합니다.

## EXE 용량 및 시작 지연 개선 제안

현재 publish.ps1은 self-contained, PublishSingleFile, IncludeNativeLibrariesForSelfExtract, EnableCompressionInSingleFile을 사용합니다. 즉 .NET 및 WPF 런타임을 EXE에 포함하고 압축합니다. 이전 빌드 EXE는 76,718,978 bytes(약 73.2 MiB)였습니다. 사용자 데이터와 로그가 EXE에 추가되는 구조는 아닙니다.

Microsoft는 단일 파일 압축에 시작 성능 비용이 있다고 설명합니다. 네이티브 라이브러리 추출, 보안 검사, JIT, 앱 생성자의 DB 및 플러그인 로딩도 측정 대상으로 봐야 합니다. 실제 사용자 PC에서 각 원인별 지연은 아직 측정하지 않았습니다.

| 선택지 | 장점 | 비용/조건 |
| --- | --- | --- |
| 권장: 설치 프로그램 + framework-dependent 배포 | 앱에 런타임을 넣지 않아 배포 크기를 줄이고 압축 해제 부담을 피함 | .NET 10 Windows Desktop Runtime x64를 최초 한 번 설치/확인해야 함 |
| 설치 프로그램 + self-contained 일반 폴더 배포 | 런타임 별도 설치 없이 실행 시 압축 해제 부담을 피함 | 전체 설치 용량은 큼. 파일은 설치 폴더 안에 두고 사용자에게 바로가기만 제공 |
| 현재 단일 EXE의 압축만 해제 | 적은 변경으로 압축에 의한 지연 감소 가능 | EXE 크기는 오히려 증가하므로 용량 문제를 함께 해결하지 못함 |

다음 단계는 세 배포본의 EXE/전체 폴더 크기, 최초 실행 및 반복 실행의 첫 화면 표시 시간을 같은 PC에서 비교하는 것입니다. 런타임 설치가 없는 PC도 확인해야 합니다. 설치형을 채택하면 사용자는 설치파일 하나와 바로가기를 사용하고 플러그인은 설치 폴더에 유지할 수 있습니다. 이 변경에서는 배포 방식은 유지하고 UI를 갱신했습니다.

공식 근거: https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview

## 검증

연결 교체 후 ID/경로/제외/속도 보존, 없는 ID의 수정 거절, ID 충돌 시 원자적 실패, 기존 로컬 파일 보존을 자동 검사합니다. 실제 계정 팝업 탐색과 시작 시간은 수동 확인 대상입니다.

수동 확인: 추가 팝업 닫기/재열기, 저장하지 않고 닫기, 저장 계정 재연결, 기존 원격 폴더 선택, 로컬/원격 변경 후 재실행, 설정 내 검사·복구·삭제, 작은 화면에서 스크롤과 오류 메시지를 확인합니다.
