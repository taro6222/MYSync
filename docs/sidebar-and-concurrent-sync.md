# 사이드바 · Google 덮어쓰기 · 병렬 전송 (2026-09-08)

## 변경 사항

- 전체 화면을 왼쪽 사이드바로 통합: 동기화, 동기화 추가, 전송, 알림·오류, 설정. 기존 오류 알림의 페이지 이동과 수동 실행 기능을 유지한다.
- Google v3 응답에 ETag가 없으면 v2 메타데이터의 ETag와 동일 파일 ID·버전을 확인하고 v2 조건부 업데이트를 사용한다. 소용량 multipart와 대용량 resumable 업로드 모두 적용한다. 조건 정보를 얻지 못하거나 버전이 바뀌면 해당 변경을 거부한다. 무조건 덮어쓰기는 하지 않는다.
- Google이 SHA256을 제공하면 전체 검사에서는 이 값을 사용해 파일 전체 다운로드를 줄인다. 파일 전송 직전의 개별 재검증, 해시 검증 및 조건부 게시를 유지한다.
- Google/로컬의 독립된 파일 업로드·다운로드를 최대 3개 병렬 처리한다. 같은 경로는 중복 실행하지 않는다. 폴더 생성, 삭제, 충돌 사본 작업은 순서를 지키며 병렬 작업과 겹치지 않는다. 속도 제한은 연결의 세 작업이 공유한다.
- 선택적 IFileStateEndpoint 계약을 추가했다. 병렬 처리를 명시적으로 지원하는 Provider만 참여한다. 기존 WebDAV와 외부 플러그인은 순차 실행을 유지한다.
- 파일 오류가 나도 나머지 작업을 실행하고, 정상 완료한 경로의 비교 기준을 개별 저장한다. 자동 감시는 확인 필요 이후에도 파일 변경·정기 검사를 계속한다. 정기 검사는 기본 5분이다.
- 새 전체 검사로 오래된 작업 계획을 갱신한다. 동일한 충돌 작업 ID·사본은 유지하며, 새 파일이나 수정된 파일이 과거 실패 작업에 막히지 않는다.
- 구버전의 Applied(반영됨) 기록에 저장된 게시 버전을 비교 기준에 복원한다. 최종 수렴 전에 다음 수정이 발생해도 최초 충돌로 잘못 판단하지 않도록 한다.
- 정상 파일은 전송 목록에서 개별 완료로 표시한다. 실제 동시 수정 충돌은 양쪽 원본과 보존 사본을 유지하고 사용자의 선택을 기다린다.

## 진단 근거와 범위

사용자의 배포 로그에서 Google HTTP 200 응답에 강한 ETag가 없는 것을 확인했다. 로컬 Google 작업 DB에는 Applied 10건이 있고 전역 비교 기준이 없었다. 오류 상세 기록은 없어서 당시 최종 비교가 실패한 정확한 파일까지 특정하지는 못했다. 사용자 DB와 실제 원격 파일은 진단 중 수정하지 않았다.

전체 검사가 불완전하거나 미확인 로컬 복구 기록이 있으면 해당 연결의 쓰기를 보류한다. 일부 파일이 실패한 것과 전체 목록을 신뢰할 수 없는 것은 구별한다. 서버 조건부 요청 집행과 실제 계정 권한은 실서버 검증이 필요하다.

## 검증

build.ps1 -Check 전체 검증에 다음 회귀 시나리오를 추가했다.

- v3 ETag가 없는 소용량 교체·휴지통 이동, v2 ETag 누락 거부, 교체 직전 외부 변경 보존.
- 9 MiB 초과 파일의 v2 resumable 덮어쓰기와 청크 수 검증.
- 서버 SHA256을 이용한 검사에서 파일 데이터 다운로드가 발생하지 않음.
- 실제 로컬 파일과 지연·권한 오류 어댑터로 동시 처리 수 2~3개, 폴더 의존성 검증.
- 파일 하나가 실패한 뒤 다른 파일의 수정·신규 파일 전송, 실패 파일 내용 변경 후 최신 계획으로 복구.
- 양쪽 동시 수정 원본 보존 및 충돌 이후 다른 파일 갱신.
- 구버전 Applied 기록만 있고 기준이 없을 때 이후 수정이 Upload로 계산됨.
- 파일별 취소·재개, 응답 유실 재검사, 기존 WebDAV·복구·충돌 검증 유지.

실제 Google Drive/NAS에 대한 쓰기 테스트는 수행하지 않았다. 새 EXE에서 자동 동기화를 시작하고 로컬 파일 수정 → 원격 내용 확인 → 원격 수정 → 로컬 확인을 진행한다. 여러 파일 전송 중 하나를 중지해 다른 파일이 계속 처리되는지 확인한다. 양쪽을 동시에 바꾼 파일은 충돌·복구에서 선택한다.
